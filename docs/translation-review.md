## 资源与限制

认证读取本次实际运行的 `/props`：`n_ctx=262144`、`n_predict=-1`、`max_tokens=-1`。应用没有设置 `--ctx-size`，不将模型标称容量当成可稳定完整翻译的长度保证。

一次短翻译后，模型进程 `ps rss` 为 8,539,120 KiB，约 8.14 GiB。这只是该时刻进程 RSS，不是 macOS physical footprint、Metal 完整资源或峰值。不同请求和运行时适配会改变占用，不能套用旧报告 8K 上下文的内存数字；本轮没有重新做系统级峰值测量或精确延迟统计。

应用不限制字符、输出 token、响应正文或推理等待时长。单次 HTTP 使用 `node:http.request`，不受 Node fetch 的隐含响应头等待限制；AbortSignal 关闭连接。模型原生超时、上下文、内存和平台限制仍可能终止请求。首次模型启动保留独立的 60 秒健康检查保护，不是生成时间预算。

错误级 stderr 只保留在内存；进程 `close` 排空后展示原始诊断，不写翻译历史或文本日志。请求错误与原生错误不互相遮蔽，同一诊断不重复显示。

## Review 与边界

只读代码 Review 发现并修复：非流式 fetch 隐含五分钟响应头超时，以及 ready 后丢失原生 stderr。复核未发现新的重要问题；没有用静态检查代替实机验证。

- 未验收打包版、Finder 启动环境变量传递、Intel 或小内存机器；模型和 runtime 未加入打包配置，也未再次生成应用包。
- 未模拟系统断网。本地链路仅访问 loopback，使用既有文件并以 `--offline` 启动；这不等于阅读网站、DeepSeek 或字幕获取也能离线。
- 未验证完整 262K 长文的翻译质量、资源峰值，或耗时超过五分钟的实际完整译文；transport 无应用超时经代码与原生文档复核。
- 未注入 Metal 致命故障或模拟应用被 SIGKILL；正常退出清理已实测，不承诺强杀主进程后无孤儿进程。
- 原有阅读问答、字幕能力不在本轮付费/线上全量回归范围，未将它们替换为本地模型。

## 2026-10-07 后台预热复验

启动时机改为可信应用界面 `loadURL` 完成之后，主进程非阻塞调用既有 `ensure`。后台预热与翻译请求共用启动 Promise；错误仍通过模型状态发布，不自动重试，不改变模型路径、运行参数、请求或退出机制。

| 场景 | 实际结果 |
| --- | --- |
| 未进入翻译页、未提交请求 | 阅读首页正常展示，已出现本应用启动的模型子进程；首次进入翻译页显示“就绪” |
| 预热后首次翻译 | `The meeting starts at 9:30 tomorrow.` 返回 `会议将于明天 9:30 开始。`；最终代码重启后 `Could you give me a hand?` 返回 `能帮我一把吗？` |
| 复用进程 | 最终代码首次翻译前后仅有同一模型 PID，没有为翻译再启动一个进程 |
| 权重缺失 | 临时启动环境指向不存在的 GGUF，阅读首页仍正常显示；翻译页显示服务失败及原始 ENOENT，可返回阅读，不保存路径或修改配置 |
| 正常退出 | 两轮有效模型运行均用 `Cmd+Q` 退出，核对对应 Electron 与模型 PID 已不存在；开发服务器也已结束 |

`pnpm check` 和 `git diff --check` 通过，未新增依赖或仓库测试脚本。独立只读 Review 复核未报告预热、进程复用或退出清理方面的新增确认缺陷。

模型内存现在提前到应用启动后占用，即使尚未翻译也会驻留。预热只是将冷启动等待提前，不能降低实际推理时间；在预热未完成时立即提交仍需等待。此次不是精确延迟或资源基准测评，未验收打包版、Intel、启动过程中强杀主进程或系统断网。
